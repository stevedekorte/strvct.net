# AI Reviews — Plan

Status: built into colvmn (2026-11-12) and turned on in strvct's colvmn.json. colvmn produces the reviews itself (decided 2026-11-12: "just work" given colvmn, its config and keys); the strvct-side reviews.js below became colvmn's update/ai/. Runs locally on the Mac Studio from launchd (colvmn/update/launchd-template.plist), not on GitHub (decided 2026-11-12). Waiting on: the four review keys, then the first models PR.

## Goal

Add an **AI Reviews** section to the strvct.net docs: a card on the home page leading to one review page per major AI (initially Claude, ChatGPT, Gemini, Grok). Each page holds that model's evaluation of STRVCT. Readers get an outside-ish view, including weaknesses; the author gets the same feedback that prompted this (the Gemini evaluation, 2026-11).

The section is only worth having if readers believe the reviews weren't curated. Most of this plan is about that.

## Principles

1. **Readers can check it themselves.** Every review page links to the same prompt, prefilled in that provider's own chat app.
2. **Every run is on record.** Reviews are produced by a scheduled job in the public strvct repo, so each run is in the public Actions history and its output in git. A provider share link, when there is one, is an extra.
3. **No editing, no rerolling.** The first answer is published as-is, criticism included. This policy is stated on the section page.
4. **Corrections sit beside the review, never in it.** An optional *Author's note* below the review corrects factual errors.
5. **Dated, and history is kept.** A replaced review moves to a dated archive instead of disappearing.
6. **Not an endorsement.** Each page says: "Generated by [model] on [date]; not an endorsement by [provider]."

## The Prompt

One prompt, shared by all providers, kept in config, short enough to fit in a URL. It must not reveal who is asking: the Gemini thread got noticeably warmer after "I wrote it".

Draft:

> Read https://strvct.net/llms.txt and the pages it links. Ignore the "AI Reviews" section. Evaluate STRVCT: what it is, its strengths, its weaknesses and risks, who should and shouldn't use it, and how it compares to alternatives. Begin by quoting the site build stamp you saw, then give your verdict in one sentence of at most 20 words.

No numeric scores, since they invite gaming and out-of-context screenshots.

The scheduled job calls the APIs, which don't browse, so it sends the same prompt with `llms-full.txt` attached in place of the URL. The site's own text, build stamp included, is then exactly what every model sees. The prefilled links use the URL form; the review page shows both.

## Build Stamp

colvmn writes a stamp naming the **release**, e.g. `STRVCT · 2026-11-12 · 3c23b7bb`, into the page footer and the top of `llms.txt` / `llms-full.txt`. A release is any push of code (decided 2026-11-12; see `notes/Generated Docs Plan.md`), so the stamp names the pushed commit. It doesn't change when the reviews job commits, because that push isn't code: otherwise each reviews run would change `llms-full.txt` and retrigger itself. The prompt asks the model to quote it, which:

- ties each review to an exact version of the docs;
- shows whether the model actually read the site (no stamp quoted → it answered from memory).

Useful on its own; do this first.

## Review Pages

Each review lives in its page's `_index.md`, formatted for reading like any other docs page. The top of the page links to the origin with the prompt, so readers can check it easily even if the check isn't perfect. Being useful matters more than being a proof (decided 2026-11-12).

Each page shows, in order:

- at the top: the model name, the date, the build stamp the model quoted, and the links: **Ask [model] yourself →** (the prefilled URL; where there isn't one, a link to the app and the prompt to copy) and **View the original conversation →** (a share link, when there is one);
- the review text, formatted;
- an optional **Author's note** with corrections.

The section page states the policy (principles 3–6), the prompt, and that answers vary by account, plan and settings.

**The home-page card's text is fixed.** No dates, counts or quotes from the reviews: the home page is in `llms-full.txt`, so anything there that changes per run would feed the reviews' own trigger.

## Producing Reviews

Reviews are produced by colvmn's scheduled updates (`colvmn/docs/plans/scheduled-updates/_index.md`). Two jobs, both in the AI Reviews folder of the strvct site, both **script jobs**: they need four API keys, and colvmn gives credentials only to scripts, never to prompt jobs.

**The models job** (`AI Reviews/models/_update.md`): daily. Finding each service's latest top model ID is part of the review process, and this job does it. A script reads each provider's model list and, when it finds a likely newer top model, updates `models.json`. A model list says what exists, not what's top, so the script guesses: the newest model in the provider's flagship family, skipping mini/flash/preview/dated-snapshot variants. Because a published review is never withdrawn or rerolled, a wrong guess must not reach a review unchecked, so the job publishes as a **PR** and a human confirms; the reviews job only ever uses a confirmed `models.json` (decided 2026-11-12: keep the PR step rather than fold model selection into the reviews run).

`models.json`, one entry per provider: `{ "Claude": { "id": "<API model ID>", "name": "<full model name>" }, ... }`. The full name is what review pages and cards show; the ID is what the API is called with and what Details shows.

**The reviews job** (`AI Reviews/_update.md`):

```yaml
run: reviews.js
schedule: daily
watch: ["llms-full.txt", "AI Reviews/models/models.json"]
minInterval: 30d
secrets: [ANTHROPIC_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY, XAI_API_KEY]   # built in now: the providers' standard keys (decided 2026-11-12), or names from aiReviews "keys"
writes: ["AI Reviews/**"]
publish: direct
```

- **Due** when `llms-full.txt` (exactly what the models read, with the reviews already excluded) or `models.json` changed since its last run, at most once per `minInterval`. A merged model bump therefore triggers a review on the next nightly check; daily doc edits don't cause daily reviews. (Per provider, ideally: a new Claude model shouldn't redo the other three. The script can compare each provider's last review against `models.json` and skip the unchanged ones.)
- **The script decides what's really changed.** For each provider it hashes `llms-full.txt` with the stamp line removed, together with the model ID, and skips the provider when both match the current review. If all four are skipped, it exits with colvmn's "nothing to do" status: no commit, no rebuild. So `watch` only decides whether to check, and a false alarm costs a hash, not four reviews.
- **Each run** sends the prompt with `llms-full.txt` to each provider that changed, writes the review into that provider's `_index.md` with its metadata (full model name, model ID, date, quoted stamp, the one-sentence verdict as `summary`, input hash), and moves the previous review to the archive. The verdict is the model's own words, taken as written: it is the text of the provider's card on the section page, under the full model name (decided 2026-11-12).
- **Publishes directly.** A completed answer is published as it is; only a run that errors is retried. No human picks between outputs.
- **Runs on a GitHub-hosted runner** in the public strvct repo, with the four keys as GitHub Actions secrets, each with a low spend limit. This is the "credentialed jobs on public repos" path proposed in the colvmn plan; the Mac Studio runner serves only private repos. The public run history is the no-reroll record.
- **Where it runs is open** (2026-11-12): a GitHub-hosted runner keeps the run history public; the Mac Studio (launchd running `node colvmn/update.js --push`) keeps everything local but the history private. Either way it can be run by hand: `node colvmn/update.js --folder "AI Reviews"`.

**Share links (optional, manual).** When a new top model arrives, the same prompt can also be run in that provider's chat app from a clean account (memory and custom instructions off) and the conversation shared, as a spot check that the app agrees with the API. The link goes in the page's metadata. API calls can't create share links, so this stays manual.

Seeds don't help: Claude's API has none, and OpenAI and Gemini document theirs as best effort, so readers can't replay a review.

## Keeping Reviews Out of llms.txt

The reviews must not be in `llms.txt` / `llms-full.txt`:

- **Feedback loop:** later reviews would read earlier ones and anchor on them, including their mistakes.
- **Purpose:** `llms.txt` is factual documentation for agents using STRVCT; reviews are unedited third-party opinion.

colvmn change: a page-level `_index.json` option, e.g. `"llms": false`, that leaves a page and its subtree out of both llms files (they stay in the sitemap). Check whether `_unused` pages currently leak into `llms-full.txt`; if so, the same option fixes them. The prompt's "Ignore the AI Reviews section" covers models that browse there from the home card anyway.
