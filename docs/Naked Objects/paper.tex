\title{Closing the Usability Gap in Naked Objects}
\subtitle{From Domain Models to Complete Applications}

\author{Steve Dekorte}

\begin{abstract}
The \textbf{Naked Objects} architectural pattern proposes that complete user interfaces can be derived automatically from domain models. Instead of manually maintaining separate models, component trees, form layouts, validators, persistence mappings, localization files, and AI tool specs, developers declare their domain logic once and allow the runtime engine to project it into every required form.

While early Naked Objects systems successfully demonstrated this derivation, they relied on a narrow grammar---rendering objects as forms and collections as tables. This created a severe ``usability gap'' that restricted Naked Objects to internal tools and administrative backends.

This paper presents a modern, flexible interaction grammar that closes this usability gap without requiring hand-authored UI component trees. We treat every screen as a \textbf{lens} over the model's object graph, and show that most interactions in structured-information software reduce to two core operations on that lens: (1)~\textbf{moving the lens}---traversing relationships across the object graph via recursive, orientation-flexible master-detail views (Miller columns), and (2)~\textbf{shaping the lens}---deciding whether each visible child is layered or inlined, and arranging collections along semantic dimensions (such as linear feeds, inline documents, anchored tabs, and aligned matrices).

We demonstrate \textbf{Strvct}, an open-source client-side framework implementing this model-driven approach. By centralizing the model-to-view pipeline through slot metadata annotations, Strvct delivers architectural capabilities ``for free'': automatic responsive collapse, headless testability, transparent persistence and cloud synchronization, unified accessibility, and a natively AI-operable agent projection with a constant-size tool surface.

In a production case study (\textbf{undreamedof.ai}, an AI tabletop gaming platform with $\sim$90 domain classes), $\sim$98\% of all views are framework-generated. The remaining custom views are inherently graphical media (a 3D dice engine and a battle map), confirming that the boundary of automatic UI generation falls naturally where spatial geometry carries irreducible domain meaning.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Modern software development spends immense effort creating and maintaining user interfaces. In traditional component frameworks (such as React, Vue, or Svelte), every screen is authored as a bespoke artifact. When a data model changes---such as adding a field to a customer profile---the developer must manually update:
\begin{itemize}
\item The domain model class
\item Form UI layouts and input fields
\item Client-side and server-side validation rules
\item Persistence schemas and ORM mappings
\item Navigation graphs and routing states
\item Localization string dictionaries
\item Accessibility ARIA attributes
\item AI agent tool definitions and API endpoints
\end{itemize}

This structural duplication creates exponential maintenance costs and frequent synchronization bugs.

\begin{verbatim}
Traditional Component Approach (Manual Propagation):
Domain Model -> UI Components -> Forms -> Validators -> Persistence -> AI Specs

Model-First Naked Objects Approach (Automatic Projection):
                 +-> UI Projection (Master-Detail, Tabs, Docs;
                 |                  Accessible & Localized)
                 |-> Storage Projection (Local Pools & Cloud Sync)
Annotated Model -+-> Exchange Projection (JSON Import, Export & Patches)
                 |-> Agent Projection (Constant-Size AI Tool Surface)
                 +-> Headless Execution & Fast Testing
\end{verbatim}

\textbf{Naked Objects}, introduced by Pawson and Matthews in 2002~\cite{pawsonbook}, proposed a radical alternative: expose domain objects directly to users and generate the entire interface automatically. Because there is no separate UI code, consistency is guaranteed---the interface always perfectly reflects the live state of the domain.

Despite its obvious maintenance benefits, early Naked Objects implementations (such as Apache Isis/Causeway~\cite{causeway}) struggled with widespread adoption. They derived every object into a form and every collection into a table. While functionally complete, these interfaces felt rigid. They lacked spatial context, viewport adaptability, depth indicators, and visual continuity.

This paper shows how to close that usability gap. We contend that the design space for information management software is remarkably narrow and structured. By replacing generic forms and tables with a richer grammar---\textbf{recursive relationship traversal} and \textbf{semantic collection arrangement}---frameworks can derive modern, beautiful, and responsive interfaces directly from annotated models.

The key step is a change of picture. Rather than thinking of an application as a set of screens, we think of it as one complete projection of the model's object graph, and of each screen as a \textbf{lens} through which part of that projection is seen (\S\ref{sec:lens}).

\section{The Usability Gap in Prior Systems}
\label{sec:gap}

To understand why classic Naked Objects stalled, we must examine the specific usability limitations of early form-and-table systems:

\begin{enumerate}
\item \textbf{Lack of Spatial Hierarchy:} Generic forms flatten relationships into lists of text boxes and dropdowns. Users cannot visually perceive ownership, containment, or structural depth.
\item \textbf{Limited Viewport Adaptability:} Form-based tools are typically designed for fixed desktop resolutions. Adapting them to mobile screens requires ad-hoc, per-screen responsive hacks.
\item \textbf{Loss of Context During Navigation:} Drilling into a child object in a form interface usually replaces the screen or pops up a modal window. Each screen becomes a disconnected island, and users never form a picture of the object graph as a whole.
\end{enumerate}

Component frameworks (React, Vue) address this problem by giving developers total visual freedom, but at the cost of authoring every screen by hand. Our goal is to achieve the visual quality and spatial legibility of hand-crafted apps while keeping the zero-UI-maintenance benefits of Naked Objects.

\section{The Model as a Graph, the Screen as a Lens}
\label{sec:lens}

Before describing the grammar itself, it helps to picture what a generated interface is actually showing.

Imagine the domain model as a graph: a tree of ownership, with symbolic links for the references that cross it. Now imagine drawing all of it at once---every object, every property, every collection, fully expanded. This drawing is the model's complete \textbf{UI projection}. It is faithful and complete, and for any real application far too large to look at.

Every screen the user sees is a \textbf{lens} over that drawing. At first order, a lens makes only two decisions:

\begin{enumerate}
\item \textbf{Visibility:} Which nodes to collapse. Typically everything off the current navigation path is collapsed, leaving the path itself and the immediate children of the nodes along it.
\item \textbf{Placement:} For each visible parent$\rightarrow$child edge, whether the child is \textbf{layered} (given its own plane beside or in front of its parent, as in Miller columns, push stacks, and tabs) or \textbf{inlined} (drawn within its parent's extent, as in documents, grouped sections, and side-by-side panes).
\end{enumerate}

\begin{figure*}[t]
\centering
\includegraphics[width=0.85\textwidth]{lens-placement.pdf}
\caption{One Projection, Three Lenses: a small model graph as its full UI projection, and through layering, inlining, and mixed lenses.}
\label{fig:lens-placement}
\end{figure*}

Layering and inlining are not modes of the whole interface but choices made edge by edge, and they compose freely. A layered column may hold an inlined document whose link opens another layer; a document section may itself be a set of anchored tabs. The mixed lens in Figure~\ref{fig:lens-placement} inlines \emph{Project}'s sections in one column and layers \emph{Task 2} into the next, and even the pure inlining lens layers its link to \emph{Person}. Because the choice lives on each edge rather than on each screen, it can change without touching the model---set by a developer's hint, or switched by the framework as space changes.

At second order, a lens decides \textbf{arrangement}: how siblings within a layer or an inlined run are laid out---their orientation, whether their properties align across siblings into a table, or whether a value maps to position, as on a timeline (\S\ref{sec:traversal-arrangement}).

This framing reduces an apparently unbounded space of screens to something tractable. Any screen is a path through the graph, plus a placement for each visible edge and an arrangement for each visible collection. That is a small, regular decision space---small enough for the framework to own its mechanics (the path, collapse, layering, inlining, and responsive switching) while the developer states intent through hints on the model: which edges inline, which layer, how collections arrange. The decisions are the developer's; their implementation is the framework's.

It also explains behaviors that would otherwise have to be built screen by screen:
\begin{itemize}
\item \textbf{Navigation} is moving the lens. Traversing a relationship changes the path, not the model.
\item \textbf{Responsive collapse} is the lens switching edges from inlined to layered as space runs out, within the bounds the hints allow. Miller columns that collapse into a push stack are still layered---in depth rather than side by side. Side-by-side panes that degrade to tabs are the same edge moving from inlined to layered.
\item \textbf{Links} are followed by layering. Inlining a link would draw its target inside the referrer, and a cycle of links would expand forever; layering keeps every lens finite and makes the crossing visible.
\end{itemize}

None of these decisions is new to the literature. Furnas's fisheye views~\cite{furnas1986} formalize visibility as a degree-of-interest function over a tree; overview+detail and focus+context interfaces~\cite{cockburn2008} separate or blend levels of detail much as layering and inlining do; and tree visualization distinguishes children drawn \emph{within} their parents (inclusion) from children drawn \emph{beside} them (adjacency)~\cite{schulz2011}. Inlining a linked target is what Nelson called transclusion~\cite{nelson1981}. Systems such as Furnas's, APT~\cite{mackinlay1986}, and SUPPLE~\cite{supple2004} go further and compute the presentation---by interest score, by search, or by optimization. Strvct deliberately does not. It owns the mechanism and supplies the defaults; the developer states intent through hints, much as a projectional editor lets a language designer declare the notation through which a model is edited~\cite{voelter2014}.

Our use of \emph{lens} differs from the Magic Lenses of HCI~\cite{bier1993}, which filter a local region of the screen. It is closer to the lenses of bidirectional programming~\cite{foster2007}: editable views whose changes flow back to their source, as edits in a Strvct view flow back to the model.

The UI projection is not the only one. The same graph is projected into records in object pools (the \textbf{storage projection}), into JSON for import, export, and patching (the \textbf{exchange projection}), and into a schema-and-patch tool interface for AI agents (the \textbf{agent projection}, \S\ref{sec:ai-operable}). Each is a different reading of the same annotated model; none is authored separately.

\section{A Narrow Design Space for Information Apps}
\label{sec:narrow}

A common misconception is that auto-generation forces all apps to look like boring administrative dashboards. However, a deeper analysis of consumer and enterprise software reveals a powerful pattern:

\begin{quote}
\textbf{Most interactions in structured-information applications consist of traversing relationships among domain objects and arranging collections of those objects along semantic dimensions.}
\end{quote}

Consider CRMs, project management tools, email clients, social networks, healthcare records, e-commerce stores, and settings panels. Although their visual styling differs, their fundamental operations are identical: users find an object, follow a relationship, inspect or edit details, and organize collections.

\begin{verbatim}
Typical Domain Graph:
Workspace
+-- Projects
|   +-- Project
|       +-- Tasks
|       +-- People
|       +-- Milestones
+-- Customers
+-- Documents
\end{verbatim}

\subsection{Relationship Traversal vs. Collection Arrangement}
\label{sec:traversal-arrangement}

In terms of the lens (\S\ref{sec:lens}), we divide the user interface grammar into two distinct layers:

\begin{itemize}
\item \textbf{Relationship Traversal:} Moving the lens along links in the object graph (e.g., from a \emph{Project} to its \emph{Tasks}, then to a specific \emph{Task}).
\item \textbf{Collection Arrangement:} Displaying a set of related objects in a specific semantic layout (e.g., viewing \emph{Tasks} as an ordered list, a Kanban board grouped by status, a table, or a timeline).
\end{itemize}

\subsection{The Boundary of Automatic Generation}
\label{sec:boundary}

Where does automatic generation end and custom code begin? The boundary is clean and objective:

\begin{itemize}
\item \textbf{Generated UI (Domain Model):} Managing structured data where spatial layout is purely an organizational aid (text, relationships, properties, categories, dates).
\item \textbf{Custom UI (Specialized Media):} Surfaces where spatial position carries \emph{irreducible domain meaning}.
\end{itemize}

Examples of surfaces requiring custom UI renderers:
\begin{itemize}
\item \textbf{Creative tools:} Canvas drawing, code editors, rich audio/video sequence editors.
\item \textbf{Graphical visualizations:} 3D game viewports, interactive geographic maps, medical imaging scans.
\item \textbf{Data plots:} Complex financial or scientific charts.
\end{itemize}

For a CRM or settings panel, generated UI covers $\sim$100\% of the app. For an IDE or game, generated UI handles the application shell (file trees, properties, settings, inventory), while a specialized custom renderer powers the central canvas.

\section{Architecture \& UI Mechanics in Strvct}

Strvct implements this two-part grammar using client-side JavaScript. Master-detail views are its layering lens (\S\ref{sec:master-detail}); inline layouts are its inlining lens (\S\ref{sec:inline}). The core visual building blocks are \textbf{Tiles}, \textbf{Tile Stacks}, and \textbf{Master-Detail Views}.

\section{Model Declarations \& The Annotation Bridge}
\label{sec:annotation-bridge}

Developers define domain models as JavaScript classes inheriting from \texttt{SvStorableNode}. Properties are declared as \textbf{slots} enriched with metadata annotations:

\begin{verbatim}
(class Character extends SvStorableNode {

    initPrototypeSlots () {
        // Name slot: String property, persisted, synced to view, editable
        {
            const slot = this.newSlot("name", "");
            slot.setSlotType("String");
            slot.setShouldStoreSlot(true);
            slot.setSyncsToView(true);
            slot.setCanEditInspection(true);
        }
        // Level slot: Number property
        {
            const slot = this.newSlot("level", 1);
            slot.setSlotType("Number");
            slot.setShouldStoreSlot(true);
            slot.setSyncsToView(true);
        }
        // Inventory relationship: Navigable child object
        {
            const slot = this.newSlot("inventory", null);
            slot.setFinalInitProto(Inventory);
            slot.setIsSubnodeField(true);
        }
    }

    subtitle () {
        return "Level " + this.level();
    }

}.initThisClass());
\end{verbatim}

\subsection{The Multi-Reader Annotation Architecture}

Slot annotations serve as a decoupling bridge. Each framework subsystem reads slot metadata independently without cross-system dependencies:

\begin{itemize}
\item \textbf{UI Layer (UI Projection):} Reads \texttt{slotType}, \texttt{canEditInspection}, and \texttt{isSubnodeField} to instantiate Property Tiles and navigate child subnodes.
\item \textbf{Persistence Layer (Storage Projection):} Reads \texttt{shouldStoreSlot} to serialize records into local storage (IndexedDB) and cloud object pools.
\item \textbf{Sync Scheduler:} Reads \texttt{syncsToView} to observe slot updates and post coalesced, deferred notifications to active views.
\item \textbf{Agent Projection:} Reads property types and constraints to auto-generate JSON validation schemas and patch tools.
\item \textbf{Localization Engine:} Reads property names and translation contexts to auto-translate labels.
\end{itemize}

\begin{verbatim}
                  +-> UI Rendering Layer (Property Tiles & Controls)
                  |-> Persistence Engine (IndexedDB & Cloud Commit)
Slot Metadata ----+-> Sync Scheduler (Weak Observer Notifications)
                  |-> AI Agent Infrastructure (Patch Schemas & Verification)
                  +-> Internationalization Engine (Label Translation)
\end{verbatim}

\section{Structural Consequences (``Free'' Capabilities)}
\label{sec:consequences}

Centralizing the model-to-view pipeline through slot annotations yields powerful architectural capabilities that traditional component frameworks must build and maintain manually for every screen:

\subsection{Natively AI-Operable Model}
\label{sec:ai-operable}

Because slot metadata describes every class, Strvct exposes a universal agent projection: a tool surface consisting of just two generic functions:
\begin{enumerate}
\item \texttt{schema-fetch}: Retrieves the slot schema for any domain class or object instance.
\item \texttt{apply-patch}: Applies a JSON patch payload to update properties or mutate child relationships.
\end{enumerate}

This tool surface remains \textbf{constant in size} regardless of whether the application contains 5 domain classes or 500. When an AI agent generates an invalid field patch, the rejected response includes the slot's schema, allowing the model to self-correct in real time.

\subsection{Headless Execution and Ultra-Fast Testing}

Domain nodes contain zero DOM or browser dependencies. The exact same domain classes run unchanged under Node.js. Unit and integration tests instantiate model graphs, invoke domain methods, and assert against slot states at lightning speed without spinning up headless browser instances (Puppeteer/Playwright).

\subsection{Transparent Persistence and Cloud Sync}

Strvct divides persistence into two unified strategies:
\begin{itemize}
\item \textbf{Local Object Pools:} Fast, synchronous IndexedDB storage for domain object state.
\item \textbf{Content-Addressable Blob Store:} Asynchronous SHA-256 keyed storage for large binary assets (images, audio, files).
\end{itemize}

Cloud synchronization sends versioned atomic commits containing only the modified slot records. Conflicts are detected deterministically per document pool.

\subsection{Universal Accessibility and Localization}

Accessibility and localization are properties of the UI projection rather than projections of their own, and both are handled at the framework primitive level: translation is applied at the model-to-view boundary, as labels leave the model. Because every view is rendered by $\sim$15 shared view classes, ARIA roles, focus management, keyboard navigation, and translation hooks are paid once. Fixing an accessibility or translation bug in a primitive tile fixes it across every screen in the entire application.

\subsection{Live Inspector \& Developer Mode}
\label{sec:inspector}

Every tile supports modifier-clicking (Option + Click) to reveal a live Property Inspector displaying all declared slots, storage flags, and validation states. Developers can toggle Developer Mode to inspect hidden internal subnodes without writing custom debugging views.

\section{Limitations \& Future Work}
\label{sec:limitations}

While Strvct successfully demonstrates the power of modern Naked Objects, several open challenges and limitations remain:

\begin{enumerate}
\item \textbf{Inherently Graphical Media:} Applications centered on canvas editing, CAD, video sequencing, or 3D gaming will always require custom view renderers.
\item \textbf{Ecosystem Isolation:} To support content-addressable bundling and zero-build client loading, Strvct uses a custom resource loader rather than standard npm/Webpack/Vite tooling.
\item \textbf{Aligned Grid Arrangements (Tables \& Spreadsheets):} While inline document flow and anchored tabs are production-proven, cross-sibling column alignment (making row tiles align into full spreadsheets) is currently a proposed framework extension.
\item \textbf{Extreme Collection Scaling:} Lazy view instantiation keeps rendering lightweight, but virtualized viewport scrolling for mega-collections ($10^5+$ items) remains an active area of optimization.
\item \textbf{User-Chosen Lenses:} Because placement and arrangement are per-edge hints rather than authored screens, users could in principle reshape their own lenses---inlining a section they always want open, or layering one they rarely need. This is possible today through the live inspectors (\S\ref{sec:inspector}), but not every hint is persisted; a supported, persistent user-facing control is future work. Engelbart's NLS gave users \emph{viewspecs}---how many levels to show, how many lines per item---for much the same purpose~\cite{engelbart1968}.
\end{enumerate}

\section{Conclusion}
\label{sec:conclusion}

For twenty-five years, the Naked Objects pattern offered an enticing promise: write the domain model, and the application will follow. Early implementations stalled not because derivation was impossible, but because forms and tables were not general or flexible enough to deliver modern user experiences.

Strvct solves this by establishing a complete, flexible interaction grammar based on \textbf{recursive relationship traversal} and \textbf{semantic collection arrangement}. By eliminating manual UI component authoring, developers eliminate view-layer maintenance, reduce synchronization bugs, and gain native AI operability, instant headless testing, transparent persistence, and universal accessibility.

As AI agents become routine co-processors of software state, the cost of maintaining separate models, UI components, and tool specs will become unsustainable. Model-first derived architectures offer a durable, elegant alternative: software where the user interface is a live, faithful projection of the domain model.
