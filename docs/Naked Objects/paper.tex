\begin{abstract}
This paper proposes a conjecture about user interfaces for structured information: that nearly every screen in such an application can be described by three decisions---which part of the object graph is \textbf{visible}, whether each visible child is \textbf{layered} beside its parent or \textbf{inlined} within it, and how sibling collections are \textbf{arranged}. We call a screen described this way a \textbf{lens} over the model. If the conjecture holds, a framework can own the mechanics of those decisions (navigation, collapse, responsive switching, editing, persistence) while the developer states only the policy, as hints on the model.

Strvct is an implementation of this idea in the \textbf{Naked Objects} tradition, which derives user interfaces from domain objects and their declared behavior. It adds a compositional interaction grammar---recursive master-detail navigation, inline documents, and responsive anchored tabs---and reuses the same model metadata for persistence, exchange, and agent interfaces. A production application, \textbf{undreamedof.ai}, shows the approach is feasible at scale; the argument for its generality rests on the reader's own experience of the interfaces they already know.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A note on what kind of document this is. We do not offer a controlled evaluation or a measured productivity comparison. What follows is a design conjecture, an implementation that makes it concrete, and a deployed application that shows it is feasible. The evidence we ask the reader to weigh is their own: test the three-decision grammar of \S\ref{sec:lens} against the information applications you know---mail clients, settings panels, issue trackers, CRMs---and see whether any screen needs a decision it cannot express. The strongest case against the conjecture would be a common, non-graphical information screen that does; we would like to hear of one. The hedges that remain in later sections mark where implementation lags the conjecture, not uncertainty about the conjecture itself.

Applications often repeat domain structure across model declarations, input controls, validation, persistence mappings, navigation, and integration schemas. A new property can require coordinated changes in several places. Shared components and schema-driven tools reduce this duplication, but application authors still commonly maintain a separate presentation structure.

\textbf{Naked Objects}, described by Pawson and Matthews~\cite{pawsonbook}, offers another approach: expose domain objects and actions through generated interfaces. Strvct retains that model-first architecture while exploring a richer set of reusable navigation and layout mechanisms.

\begin{scriptsize}
\begin{verbatim}
                 +-> UI (Navigation, Fields, Documents & Tabs)
                 |-> Storage (Local Pools & Cloud Sync)
Annotated Model -+-> Exchange (JSON Import, Export & Patches)
                 |-> Agent Interface (Schema & Patch Operations)
                 +-> Headless Domain Execution
\end{verbatim}
\end{scriptsize}

The contribution is a compositional account of those UI mechanisms and an implementation that reuses model metadata across subsystems. The division of labor matters: the framework does not infer layouts, as early Naked Objects systems did; it implements the mechanics, and the developer states intent. Domain design, presentation decisions, and testing the resulting experience remain the developer's work---but as policy, not as separately authored screens.

\section{The Usability Problem Addressed Here}
\label{sec:gap}

Generating fields and collections is only part of generating a useful application. Users also need to retain context while traversing relationships, see related information together, and navigate on small screens. This paper focuses on three design requirements:

\begin{enumerate}
\item \textbf{Visible hierarchy:} Distinguish ownership, containment, and cross-references.
\item \textbf{Context-preserving navigation:} Keep the selected path legible as users move between related objects.
\item \textbf{Reusable responsive behavior:} Adapt the same navigation structure to different viewport sizes.
\end{enumerate}

Forms and tables remain useful arrangements; the question is how they compose with other views. Existing model-driven systems also support customization: Apache Causeway, for example, documents UI extensions for maps and calendars~\cite{causeway}. Strvct's focus here is recursive composition of layered and inline views, rather than a claim that prior systems can render only forms and tables.

\section{The Model as a Graph, the Screen as a Lens}
\label{sec:lens}

This section states the conjecture from the Abstract precisely. Before describing the grammar in detail, it helps to picture what a generated interface is actually showing.

Imagine the domain model as a graph: a tree of ownership, with symbolic links for the references that cross it. Now imagine drawing all of it at once---every object, every property, every collection, fully expanded. This drawing is the model's complete \textbf{UI projection}. This is a conceptual projection of the UI-exposed model, not a drawing that the runtime must materialize; internal or hidden properties need not be exposed.

Every screen the user sees is a \textbf{lens} over that drawing. At first order, a lens makes only two decisions:

\begin{enumerate}
\item \textbf{Visibility:} Which nodes to collapse. Typically everything off the current navigation path is collapsed, leaving the path itself and the immediate children of the nodes along it.
\item \textbf{Placement:} For each visible parent$\rightarrow$child edge, whether the child is \textbf{layered} (given its own plane beside or in front of its parent, as in Miller columns, push stacks, and tabs) or \textbf{inlined} (drawn within its parent's extent, as in documents, grouped sections, and side-by-side panes).
\end{enumerate}

\begin{figure*}[t]
\centering
\includegraphics[width=0.85\textwidth]{lens-placement.pdf}
\caption{One Projection, Three Lenses: a small model graph as its full UI projection, and through layering, inlining, and mixed lenses.}
\label{fig:lens-placement}
\end{figure*}

Layering and inlining are not modes of the whole interface but choices made edge by edge, and they compose freely. A layered column may hold an inlined document whose link opens another layer; a document section may itself be a set of anchored tabs. The mixed lens in Figure~\ref{fig:lens-placement} inlines \emph{Project}'s sections in one column and layers \emph{Task 2} into the next, and even the pure inlining lens layers its link to \emph{Person}. Because the choice lives on each edge rather than on each screen, it can change without touching the model---set by a developer's hint, or switched by the framework as space changes.

At second order, a lens decides \textbf{arrangement}: how siblings within a layer or an inlined run are laid out---their orientation, whether their properties align across siblings into a table, or whether a value maps to position, as on a timeline (\S\ref{sec:traversal-arrangement}). Visibility, placement, and arrangement are the three decisions of the conjecture.

This framing reduces an apparently unbounded space of screens to something tractable. Within this grammar, a screen is described by a navigation path, placements for visible edges, and arrangements for visible collections. That is a small, regular decision space---small enough for the framework to own its mechanics (the path, collapse, layering, inlining, and responsive switching) while the developer states intent through hints on the model: which edges inline, which layer, how collections arrange. The decisions are the developer's; their implementation is the framework's.

It also explains behaviors that would otherwise have to be built screen by screen:
\begin{itemize}
\item \textbf{Navigation} is moving the lens. Traversing a relationship changes the path, not the model.
\item \textbf{Responsive collapse} is the lens switching edges from inlined to layered as space runs out, within the bounds the hints allow. Miller columns that collapse into a push stack are still layered---in depth rather than side by side. Side-by-side panes that degrade to tabs are the same edge moving from inlined to layered.
\item \textbf{Links} normally open another layer, making a cross-reference explicit. Recursive inlining also needs depth or cycle limits; layering alone does not bound the length of a navigation history.
\end{itemize}

None of these decisions is new to the literature. Furnas's fisheye views~\cite{furnas1986} formalize visibility as a degree-of-interest function over a tree; overview+detail and focus+context interfaces~\cite{cockburn2008} separate or blend levels of detail much as layering and inlining do; and tree visualization distinguishes children drawn \emph{within} their parents (inclusion) from children drawn \emph{beside} them (adjacency)~\cite{schulz2011}. Inlining a linked target is what Nelson called transclusion~\cite{nelson1981}. Systems such as Furnas's, APT~\cite{mackinlay1986}, and SUPPLE~\cite{supple2004} go further and compute the presentation---by interest score, by search, or by optimization. Strvct deliberately does not. It owns the mechanism and supplies the defaults; the developer states intent through hints, much as a projectional editor lets a language designer declare the notation through which a model is edited~\cite{voelter2014}.

Our use of \emph{lens} differs from the Magic Lenses of HCI~\cite{bier1993}, which filter a local region of the screen. It shares the editable-view intuition of bidirectional programming~\cite{foster2007}, because edits flow back to the model; this analogy does not assert the formal round-trip laws of a bidirectional lens.

The UI projection is not the only one. The same graph is projected into records in object pools (the \textbf{storage projection}), into JSON for import, export, and patching (the \textbf{exchange projection}), and into a schema-and-patch tool interface for AI agents (the \textbf{agent projection}, \S\ref{sec:ai-operable}). Each reads the same annotated model, while requiring its own framework implementation and application configuration.

\section{A Narrow Design Space for Information Apps}
\label{sec:narrow}

The conjecture's scope is structured-information applications: CRMs, project management tools, mail clients, issue trackers, settings panels, and the like. The claim is that their screens can be expressed through relationship traversal, property editing, domain actions, and semantic collection arrangements. Readers can check this against interfaces they use: a mail client is a layered column of mailboxes, a layered column of messages, and an inlined message body; a settings panel is a vertical master-detail with inlined groups; an issue page is an inlined document whose cross-references layer. A modal is a layered edge drawn in front rather than beside; a search result is a derived collection; a dashboard is a set of inlined siblings with quantitative arrangement.

What the grammar does not supply is the task-specific workflow---the triage sequence, the bulk edit, the pipeline report. Those remain application design, stated as domain actions and policies (\S\ref{sec:actions}) rather than as screens; the framework owns the interaction mechanics beneath them.

\subsection{Relationship Traversal vs. Collection Arrangement}
\label{sec:traversal-arrangement}

In terms of the lens (\S\ref{sec:lens}), we divide the user interface grammar into two distinct layers:

\begin{itemize}
\item \textbf{Relationship Traversal:} Moving the lens along links in the object graph (e.g., from a \emph{Project} to its \emph{Tasks}, then to a specific \emph{Task}).
\item \textbf{Collection Arrangement:} Displaying a set of related objects in a specific semantic layout (e.g., viewing \emph{Tasks} as an ordered list, a Kanban board grouped by status, a table, or a timeline).
\end{itemize}

\subsection{The Boundary of Automatic Generation}
\label{sec:boundary}

Generation covers the arrangements and controls the framework implements. A developer selects those mechanisms through metadata or node methods. A new arrangement or specialized interaction may require a new renderer; once implemented generically, that renderer can potentially serve multiple domain models.

Spatial meaning alone does not determine this boundary: both calendars and battle maps encode meaningful positions. The practical distinction is whether an existing renderer supports the required semantics and interactions. Creative canvases, code editors, 3D viewports, medical imaging, and specialized scientific plots often require additional rendering and interaction code.

An application can combine generated navigation, properties, and actions with such specialized surfaces. The amount of custom work depends on its tasks, not just its domain category.

\section{Architecture \& UI Mechanics in Strvct}
\label{sec:mechanics}

Strvct implements this grammar using client-side JavaScript: traversal (visibility and placement) through master-detail views and inline layouts, and arrangement through the collection views they contain. Master-detail views are its layering lens (\S\ref{sec:master-detail}); inline layouts are its inlining lens (\S\ref{sec:inline}). The core visual building blocks are \textbf{Tiles}, \textbf{Tile Stacks}, and \textbf{Master-Detail Views}.

\section{Model Declarations \& The Annotation Bridge}
\label{sec:annotation-bridge}

Developers define domain models as JavaScript classes inheriting from \texttt{SvStorableNode}. Properties are declared as \textbf{slots} enriched with metadata annotations:

\begin{small}
\begin{verbatim}
(class Character extends SvStorableNode {

  initPrototypeSlots () {
    // Name slot: String property, persisted,
    // synced to view, editable
    {
      const slot = this.newSlot("name", "");
      slot.setSlotType("String");
      slot.setShouldStoreSlot(true);
      slot.setSyncsToView(true);
      slot.setCanInspect(true);
      slot.setIsSubnodeField(true);
      slot.setCanEditInspection(true);
    }
    // Level slot: Number property
    {
      const slot = this.newSlot("level", 1);
      slot.setSlotType("Number");
      slot.setShouldStoreSlot(true);
      slot.setSyncsToView(true);
      slot.setCanInspect(true);
      slot.setIsSubnodeField(true);
    }
    // Inventory relationship: navigable child
    {
      const slot = this.newSlot("inventory", null);
      slot.setSlotType("Inventory");
      slot.setShouldStoreSlot(true);
      slot.setFinalInitProto(Inventory);
      slot.setIsSubnodeField(true);
    }
  }

  initPrototype () {
    this.setShouldStore(true);
  }

  title () {
    return this.name() || "Unnamed Character";
  }

  subtitle () {
    return "Level " + this.level();
  }

}.initThisClass());
\end{verbatim}
\end{small}

\subsection{Worked Example: From a Model to a Lens}
\label{sec:worked-example}

The \texttt{Character} declaration assumes an application-defined \texttt{Inventory} node class. \texttt{isSubnodeField} exposes each property as a field in the node's contents; \texttt{canInspect} also exposes it in the developer inspector. Neither persistence nor view synchronization alone makes a property visible.

With the default \texttt{nodeChildrenLayout()} value of \texttt{"column"}, selecting a character opens its fields and Inventory relationship in the next pane. Selecting Inventory traverses that relationship. On a narrow viewport, earlier navigation panes collapse and breadcrumbs retain access to the path.

To show the same contents as a document, the class can override an existing presentation hook:

\begin{small}
\begin{verbatim}
// Methods inside Character; the stored
// properties remain the same.
nodeChildrenLayout () {
  return "inline";
}

nodeInlineDepth () {
  return 1;
}
\end{verbatim}
\end{small}

If Inventory is large and should remain a navigable summary within that document, its class can override \texttt{nodeIsInlined()} to return \texttt{false}. A container that should show its children as responsive anchored tabs instead overrides \texttt{nodeSubnodesAreAnchoredTabs()} to return \texttt{true}. These are node-level policies interpreted by shared views, rather than separately authored screens.

Adding a \texttt{species} slot with the same type, visibility, persistence, and synchronization annotations as \texttt{name} makes it available to the shared field renderer and storage serializer. Labels, constraints, and presentation order still need deliberate choices. This illustrates the maintenance benefit: reuse of the field machinery rather than the elimination of presentation design.

\subsection{Actions and Workflows}
\label{sec:actions}

Domain behavior must also be exposed deliberately. An action slot names a model method, and an optional \texttt{<methodName>ActionInfo()} method supplies presentation state. For example, these members can be added to \texttt{Character}:

\begin{small}
\begin{verbatim}
// Inside initPrototypeSlots():
{
  const slot = this.newSlot("advanceLevelAction",
                            null);
  slot.setSlotType("Action");
  slot.setIsSubnodeField(true);
  slot.setActionMethodName("advanceLevel");
}

// Methods on Character:
advanceLevel () {
  if (this.level() >= 20) {
    throw new Error(
      "Character is already at the maximum level");
  }
  this.setLevel(this.level() + 1);
}

advanceLevelActionInfo () {
  return {
    title: "Advance Level",
    isEnabled: this.level() < 20,
    isVisible: true
  };
}
\end{verbatim}
\end{small}

The shared action field reads availability from the model and invokes the method; domain checks remain necessary for callers outside the UI. Slot constraints support field validation, while cross-property rules and failed operations need useful application feedback. Bulk operations and multi-step workflows require explicit domain methods and state; they do not follow automatically from navigation relationships.

\subsection{The Multi-Reader Annotation Architecture}

Slot annotations serve as a decoupling bridge. Each framework subsystem reads slot metadata independently without cross-system dependencies:

\begin{itemize}
\item \textbf{UI Layer (UI Projection):} Reads \texttt{slotType}, \texttt{canEditInspection}, and \texttt{isSubnodeField} to instantiate Property Tiles and navigate child subnodes.
\item \textbf{Persistence Layer (Storage Projection):} Reads \texttt{shouldStoreSlot} to serialize records into local storage (IndexedDB) and cloud object pools.
\item \textbf{Sync Scheduler:} Reads \texttt{syncsToView} to observe slot updates and post coalesced, deferred notifications to active views.
\item \textbf{Agent Projection:} Reads property types and constraints to auto-generate JSON validation schemas and patch tools.
\item \textbf{Localization Engine:} Reads property names and translation contexts to auto-translate labels.
\end{itemize}

\begin{small}
\begin{verbatim}
              +-> UI Rendering (Property Tiles & Controls)
              |-> Persistence (IndexedDB & Cloud Commit)
Slot Metadata +-> Sync Scheduler (Weak Observers)
              |-> AI Agent Infrastructure (Patch Schemas)
              +-> Internationalization (Label Translation)
\end{verbatim}
\end{small}

\section{Shared Architectural Capabilities}
\label{sec:consequences}

Shared metadata lets framework subsystems reuse declarations. These capabilities require framework implementation, application configuration, and testing; their benefit is that much of that work is shared across generated views.

\subsection{Natively AI-Operable Model}
\label{sec:ai-operable}

The agent projection uses slot metadata for a schema-and-patch interface, described here by two generic operation types:
\begin{enumerate}
\item \texttt{schema-fetch}: Retrieves the slot schema for any domain class or object instance.
\item \texttt{apply-patch}: Applies a JSON patch payload to update properties or mutate child relationships.
\end{enumerate}

The number of operation types can remain constant as classes are added; schema volume, discovery work, and agent context do not. Invalid patches can return schema information for a correction attempt. A usable deployment must also define the exposed root objects, traversal and access rules, and how domain actions are invoked. A small tool vocabulary alone does not establish task success or low reasoning cost.

\subsection{Headless Domain Execution and Testing}

Domain classes that keep browser dependencies in the view and service layers can run under Node.js. Tests can instantiate model graphs, invoke methods, and assert slot states without browser automation. This makes domain testing cheaper; layout, focus, gestures, and browser integration still require UI tests.

\subsection{Transparent Persistence and Cloud Sync}

Strvct divides persistence into two unified strategies:
\begin{itemize}
\item \textbf{Local Object Pools:} In-memory access to loaded domain objects, with asynchronous IndexedDB persistence.
\item \textbf{Content-Addressable Blob Store:} Asynchronous SHA-256 keyed storage for large binary assets (images, audio, files).
\end{itemize}

Cloud synchronization sends versioned atomic commits containing only the modified slot records. Conflicts are detected deterministically per document pool.

\subsection{Shared Accessibility and Localization}

Accessibility and localization are properties of the UI projection rather than projections of their own, and both are handled at the framework primitive level: translation is applied at the model-to-view boundary, as labels leave the model. Shared view primitives centralize ARIA roles, focus management, keyboard navigation, and translation hooks. Fixes in a primitive can benefit every view that uses it. Application-specific labels, reading order, custom renderers, assistive-technology behavior, and translation quality still need validation.

\subsection{Live Inspector \& Developer Mode}
\label{sec:inspector}

Every tile supports modifier-clicking (Option + Click) to reveal a live Property Inspector displaying all declared slots, storage flags, and validation states. Developers can toggle Developer Mode to inspect hidden internal subnodes without writing custom debugging views.

\section{Limitations \& Future Work}
\label{sec:limitations}

Several limitations and questions remain:

\begin{enumerate}
\item \textbf{Renderer Coverage:} Canvas editing, CAD, video sequencing, and 3D gaming typically need specialized renderers and interaction policies. The generation boundary depends on the controls and arrangements available in the framework (\S\ref{sec:boundary}).
\item \textbf{Ecosystem Isolation:} To support content-addressable bundling and zero-build client loading, Strvct uses a custom resource loader rather than standard npm/Webpack/Vite tooling.
\item \textbf{Aligned Grid Arrangements (Tables \& Spreadsheets):} While inline document flow and anchored tabs are production-proven, cross-sibling column alignment (making row tiles align into full spreadsheets) is currently a proposed framework extension.
\item \textbf{Extreme Collection Scaling:} Lazy view instantiation keeps rendering lightweight, but virtualized viewport scrolling for mega-collections ($10^5$ or more items) remains an active area of optimization.
\item \textbf{Evaluation and Workflows:} As stated in \S\ref{sec:intro}, comparative usability, accessibility, and development effort have not been measured, and complex multi-step workflows are stated as domain actions rather than derived from the grammar. The planned follow-up is described in \S\ref{sec:case-study}.
\item \textbf{User-Chosen Lenses:} Because placement and arrangement are per-edge hints rather than authored screens, users could in principle reshape their own lenses---inlining a section they always want open, or layering one they rarely need. This is possible today through the live inspectors (\S\ref{sec:inspector}), but not every hint is persisted; a supported, persistent user-facing control is future work. Engelbart's NLS gave users \emph{viewspecs}---how many levels to show, how many lines per item---for much the same purpose~\cite{engelbart1968}.
\end{enumerate}

\section{Conclusion}
\label{sec:conclusion}

Strvct demonstrates a model-first approach in which shared views interpret an annotated object graph. Its implemented navigation grammar combines recursive master-detail panes, inline documents, responsive anchored tabs, and presentation delegation. The lens model explains how these mechanisms can compose without a separately authored component tree for every screen.

The deployed application shows the grammar covers a substantial product; quantitative coverage, development cost, and comparative usability remain open, and the conjecture itself is offered for the reader to test against the interfaces they know. Tables with cross-sibling alignment and other semantic arrangements remain extensions rather than established capabilities of this implementation.

The practical promise is reduced duplication: developers maintain domain behavior and presentation intent, while the framework shares the machinery for rendering, synchronization, storage, and agent access.
